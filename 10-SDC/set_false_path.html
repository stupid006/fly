CHAPTER 01

False path：声明哪些检查不适用

False path（假路径）是设计中存在、但在指定分析条件下不应按常规时序要求检查的路径。set_false_path 是你向 STA 工具作出的声明；工具不会因为收到这条命令，就自动证明该声明符合电路功能。

发射寄存器launch / CK → Q
→
组合逻辑延迟仍存在
→
捕获寄存器匹配检查：FALSE

把一条本来要求“下一拍之前到达”的路径设为 false，并不会让它变快。它表示当前分析不再用该要求判定这条路径是否违例。默认不写 -setup / -hold 时，两类检查都被排除；只写其中一种则只影响相应类别。

先问设计意图，再选命令

功能上永远无法激活的组合路径、当前固定模式不使用的通路，以及没有固定相位关系的跨域传输，可能需要例外。普通同步路径只是延迟大、难收敛，并不能因此变成 false path。

实际意图考虑的建模方式关键差别
该路径的检查不适用set_false_path对匹配路径豁免检查。
功能允许数据在多拍后捕获set_multicycle_path仍有时序要求；setup 和 hold 的边沿关系都需要推导。
路径必须满足明确延迟预算set_max_delay / set_min_delay仍检查给定的最大 / 最小延迟。
当前场景控制位固定set_case_analysis传播已知逻辑值，选择实际可用通路。
某一 timing arc 不应参与分析set_disable_timing影响经过该弧的分析，不等同于特定起终点的例外。

来源与版本边界见第 11 章；PT 与 FC 的报告方法分别见第 7、10 章。

“不再报 setup/hold 违例”也不意味着自动免除 max_transition、max_capacitance 等设计规则。异步 reset 还涉及 recovery/removal，不能把数据路径的解释机械套用到所有检查。

CHAPTER 02

设置以后，report_timing 还会报吗？

在通常只报告受约束路径的设置下，完全被 false 覆盖的检查不会作为普通 setup/hold 路径报出。对一组精确起终点查询可能得到 No paths.；查询范围较宽时，也可能返回范围内其他仍有效的路径。

你看到的现象合理解释下一步
普通 max 报告没有原路径可能被 false，也可能被 case analysis、禁用弧、时钟缺失或筛选条件排除。检查例外和建模，不以“没报”作为唯一证据。
max 不报，min 仍报可能只设置了 -setup。核对 setup/hold 范围。
相同寄存器对仍然出现可能换了 launch/capture clock、数据边沿、经过点或场景。比较完整 path identity，而不只是寄存器名。
调试报告显示 false / unconstrained可能启用了未约束路径搜索。这是展示被排除的原因，并不代表恢复正常检查。

PT 用 -exceptions；FC 本文版本用 -exception

Tcl · PrimeTime
report_timing -from [get_pins u_src/CK] \
    -to [get_pins u_dst/D] -delay_type max \
    -exceptions dominant

dominant 显示影响当前已报路径的主导例外；overridden 显示被覆盖的例外；all 显示两者。这里说的是 PrimeTime 的完整拼写。Fusion Compiler T-2022.03-SP4 的 SYNTAX 与 ARGUMENTS 列出 -exception dominant，且该版只接受 dominant；不能把 PT 的 -exceptions all 直接用于 FC。FC 手册部分注释也出现复数拼写，本文按正式语法栏区分，实际版本再用 man report_timing 核对。

不要把 dominant 当作“强制显示所有 false path”的开关。

要调试被排除的路径，可尝试开启 timing_report_unconstrained_paths，再按真实起终点查询。它不保证枚举所有 false path；时钟组关系、无可遍历路径、case analysis 等仍可能使查询没有结果。完整步骤见第 7 章。

来源与版本边界见第 11 章；PT 与 FC 的报告方法分别见第 7、10 章。

CHAPTER 03

-from / -to / -through：先定义集合，再匹配路径

语法示意 · 不是可执行脚本
# 常用骨架；尖括号是占位说明，不能原样执行
set_false_path [-setup | -hold] [-rise | -fall] \
    -from <合法起点集合或时钟集合> \
    -through <途经对象集合> \
    -to <合法终点集合或时钟集合>

-from、-through、-to 可按意图省略，但至少指定有效的路径范围。-rise/-fall 限定终点数据转换；与 -rise_from [get_clocks …] 限定发射时钟边沿不同。默认不写 rise/fall 时，两种数据转换都包括。

匹配 = 起点条件 AND 途经条件 AND 终点条件 AND 检查/边沿条件
  • 一个集合中的多个对象是 OR。-from {A B} 表示从 A 或 B 出发，并不是必须同时从两处出发。
  • 重复的 through 是按顺序的 AND。-through X -through Y 要求先经过 X 再经过 Y；一个 -through {X Y} 则表示经过 X 或 Y。
  • 省略一个条件，就不按该维度限制。只写 -to 可能覆盖所有到达该终点的合法路径；只写 -through 可能影响大量不同起终点。
  • 集合的笛卡尔积不等于真实路径。A/B 到 C/D 会尝试匹配四种组合，但只有实际存在、且满足其余条件的时序路径才会被约束。

对象类型：先认清 port、pin、clock、cell，再看 net

对象获取示例语义与适用位置
port
当前设计边界端口		get_ports async_req输入 port 常用作 -from；输出 port 常用作 -to。顶层看子模块接口通常是层级 pin，而不是顶层 port。
pin
实例引脚		get_pins u_src/CK
get_pins u_dst/D		普通边沿触发寄存器的数据时序路径，以发射 CK 为规范起点、捕获 D 为终点；组合逻辑引脚适合 -through。不是任意 pin 都能当合法起终点。
clock
时钟时序对象		get_clocks CLK_A-from 按 launch clock 匹配；-to 按 capture clock 匹配。还可涉及由 input/output delay 关联该时钟的 I/O，不只是内部寄存器。
cell
设计实例		get_cells u_src对普通单时钟、单数据端的寄存器，可作为起点/终点的实例级写法。组合 cell 或层级模块不是“其内部全部寄存器”的通用简写；复杂单元应明确选择合法 pin。
net
连接网络		get_nets data_link通常用于限定 -through，不能当作 clock 对象或任意合法起终点。FC 本文版本将 through net 解释为叶级驱动 pin；优先选明确 pin，避免重布线、缓冲插入后匹配范围变化。

FC 本文版本明确支持 through 的 pin / port / cell / net。其合法起点还包括 latch 的数据 pin、设置 input delay 的 pin；合法终点还包括设置 output delay 的 pin。不要把普通组合 pin、组合 cell 或 net 直接当成寄存器起终点。复杂对象的 PT 行为以本机 man 为准。

来源与版本边界见第 11 章；PT 与 FC 的报告方法分别见第 7、10 章。

Q 是数据输出，不宜直接套成 set_false_path 的规范 -from。

对于普通触发器，用 -from [get_pins u_src/CK] 或明确的寄存器 cell 表示发射起点。若要限定从 Q 出来的某支数据通路，使用 -through [get_pins u_src/Q] 并配合合适的起终点。不要从 report_timing -from Q 能否查到片段，推导例外必然具有相同语义。

集合非空，还要确认“选的是谁”

Tcl · PrimeTime
set src [get_pins u_src/CK]
set dst [get_pins u_dst/D]
puts "src count = [sizeof_collection $src]"
puts "dst count = [sizeof_collection $dst]"
puts "src names = [get_object_name $src]"
puts "dst names = [get_object_name $dst]"
if {[sizeof_collection $src] != 1 || [sizeof_collection $dst] != 1} {
    error "Expected exactly one source CK and one destination D"
}

“CK / D / Q”只是本教程的假定库引脚名。你的库可能使用 CP、CLK、QN 等名称，应从真实网表和报告获取。-hierarchical、通配符与 current_instance 会改变搜索范围；写总线名时用花括号保护 Tcl 方括号，例如 [get_pins {u_bus/data_reg[3]/D}]，并确认集合大小，避免 Tcl 替换或模式匹配造成意外。

CHAPTER 04

12 个具体 Tcl 示例

每个示例独立成立。请勿把本章所有约束连续 source 到同一场景。

01

只豁免一组寄存器之间的传输

场景前提：规格证明 u_src 到 u_dst 的传输在本场景中不会被功能使用。

Tcl · PrimeTime
set_false_path -from [get_pins u_src/CK] \
    -to [get_pins u_dst/D]

被 false 的路径

从 u_src/CK 发射、到 u_dst/D 的所有匹配数据通路，默认 setup 与 hold 都切。

未被这条约束 false

u_src → u_other；u_other → u_dst；u_dst → u_src。

读法 / 验证重点：这不是“只切报告里那一条最差路线”；若同一起终点有多条组合分支，且未限定 through，这些匹配分支都在范围内。

02

从异步输入 port 到同步器第一级

场景前提：async_req 是异步单比特电平，进入两级同步器；第一级 u_req_sync1 和第二级 u_req_sync2 均用 CLK_B。

Tcl · PrimeTime
set_false_path -from [get_ports async_req] \
    -to [get_pins u_req_sync1/D]

被 false 的路径

async_req → u_req_sync1/D 的匹配路径。

未被这条约束 false

u_req_sync1 → u_req_sync2 的同域路径；async_req 到其他终点；其他输入到 sync1。

读法 / 验证重点：必须保留第一级到第二级的时序检查，并落实同步器布局与可靠性要求。此命令不会创建同步器。

03

跨时钟域：只切 A → B

场景前提：CLK_A 与 CLK_B 的该方向传输不采用固定边沿的同步时序检查。

Tcl · PrimeTime
set_false_path -from [get_clocks CLK_A] \
    -to [get_clocks CLK_B]

被 false 的路径

由 CLK_A 发射、由 CLK_B 捕获的匹配路径；相关 I/O 若通过 delay 关联这些时钟，也可能被覆盖。

未被这条约束 false

CLK_B → CLK_A；CLK_A → CLK_A；CLK_B → CLK_B；CLK_A → CLK_C。

读法 / 验证重点：注意单向性。CLK_A_DIV2 是另一个 clock 对象，不能只凭它派生自 CLK_A 就假定本命令覆盖它。

04

跨时钟域：显式双向 false path

场景前提：两个时钟域之间的全部双向传输都采用独立审核过的 CDC 方案。

Tcl · PrimeTime
# 第 1 条：A -> B
set_false_path -from [get_clocks CLK_A] -to [get_clocks CLK_B]
# 第 2 条：B -> A
set_false_path -from [get_clocks CLK_B] -to [get_clocks CLK_A]

被 false 的路径

第一条只切 A → B；第二条补上 B → A。

未被这条约束 false

A → A、B → B；与未列出的 CLK_C 之间的传输。

读法 / 验证重点：双向需要两条有方向的声明。把 A/B 同时放进 from 和 to 集合，会连同 A → A、B → B 一起切掉。

05

用 clock groups 表达完整异步关系

场景前提：A 和 A_DIV2 同属一组；B 和 B_DIV2 同属另一组；两组整体异步，组间没有要保留的普通时序检查。

Tcl · PrimeTime
set_clock_groups -asynchronous -name ASYNC_AB \
    -group [get_clocks {CLK_A CLK_A_DIV2}] \
    -group [get_clocks {CLK_B CLK_B_DIV2}]
report_clock -groups

被 false 的路径

不是逐条 set_false_path；效果是两组之间所有方向的 launch/capture 时序关系被排除。

未被这条约束 false

组内 A ↔ A_DIV2、B ↔ B_DIV2 关系；两个已列组与未列 CLK_C 的关系不因这条两组命令自动排除。

读法 / 验证重点：它与两条 false path 在 SI 建模和报告管理上并不完全等价。这里显式列出派生时钟；不要只定义一个 group，以免把它与所有其他时钟都隔离。

06

只切经过某个 MUX 输入的支路

场景前提：u_mux/A1 支路在当前已证明的协议条件下不可被捕获；A0 支路仍需要检查。

Tcl · PrimeTime
set_false_path -from [get_pins u_src/CK] \
    -through [get_pins u_mux/A1] \
    -to [get_pins u_dst/D]

被 false 的路径

u_src → u_mux/A1 → u_dst，三个条件同时成立的通路。

未被这条约束 false

同一寄存器对经过 A0 的路线；其他源经 A1 到 u_dst；u_src 经 A1 到其他终点。

读法 / 验证重点：若改写为只剩 -through u_mux/A1，则所有经过 A1 的合法起终点都可能被切。若是固定 select 模式，优先考虑示例 11 的 case analysis。

07

两个 through：必须先 X 再 Y

场景前提：只有依次穿过 u_x/Z、u_y/A 的路线在本场景不可激活。

Tcl · PrimeTime
set_false_path -from [get_pins u_src/CK] \
    -through [get_pins u_x/Z] \
    -through [get_pins u_y/A] \
    -to [get_pins u_dst/D]

被 false 的路径

u_src → X → Y → u_dst。

未被这条约束 false

只经 X；只经 Y；先 Y 后 X；起点或终点不同。

读法 / 验证重点：through 的书写顺序就是路径上的匹配顺序。即便两个对象都存在，网表中没有该顺序的连线，也不会凭空产生一条路径。

08

一个 through 集合：X 或 Y

场景前提：从源到目的，经过 u_x/Z 或 u_y/Z 的路线均已证明不使用。

Tcl · PrimeTime
set_false_path -from [get_pins u_src/CK] \
    -through [get_pins {u_x/Z u_y/Z}] \
    -to [get_pins u_dst/D]

被 false 的路径

同一起终点之间，只经 X、只经 Y、同时经 X 和 Y 的路径，都满足这个 OR 条件。

未被这条约束 false

同一起终点但既不经过 X 也不经过 Y 的路线；其他起终点。

读法 / 验证重点：与示例 7 不同：这里只有一个 through 条件，因此不要求两个点都经过，也不指定两者次序。

09

只 false setup，保留 hold

场景前提：规格明确这条传输的 setup 检查不适用，但仍需验证 hold；此例仅演示检查类别。

Tcl · PrimeTime
set_false_path -setup -from [get_pins u_src/CK] \
    -to [get_pins u_dst/D]

report_timing -from [get_pins u_src/CK] \
    -to [get_pins u_dst/D] -delay_type min

被 false 的路径

所选路径的 setup / max 类检查。

未被这条约束 false

同一路径的 hold / min 类检查，以及所有范围外路径。

读法 / 验证重点：第二条 report_timing 不修改约束；在其余条件完整时仍可报告 hold 路径。不能把 -setup 当作“setup 收不拢”的修复手段；-hold 同理。

10

用 cell 表示普通寄存器起终点

场景前提：u_src、u_dst 都是普通单时钟、单数据端触发器，而不是层级模块或复杂宏。

Tcl · PrimeTime
set_false_path -from [get_cells u_src] \
    -to [get_cells u_dst]

被 false 的路径

这两个寄存器实例对应的合法发射到捕获路径。

未被这条约束 false

其他源/目的寄存器对；反向 u_dst → u_src。

读法 / 验证重点：该简单模型下可用于表达示例 1 的意图。对多位触发器、宏、多个时钟/数据端，不能假定选择一个 cell 就覆盖所有希望的内部路径，应用明确 pin 并验证。

11

FUNC 模式：固定 select，或精确排除测试支路

场景前提：显式数据 MUX 满足 Y = test_mode ? A1 : A0；A0 接功能源，A1 接测试源。FUNC 场景中 test_mode 保持 0。

Tcl · PrimeTime
# 方案 A：FUNC 场景采用真实模式值
set_case_analysis 0 [get_ports test_mode]
update_timing

# 方案 B：仅用于已证明 A1 支路不可用、又不能采用 A 的建模情形
# 这是独立替代方案，不要求与 A 叠加
# set_false_path -through [get_pins u_data_mux/A1] \
#     -to [get_pins u_func_dst/D]

被 false 的路径

方案 A 没有新增 false-path exception；常量传播会排除不可用的 A1 数据分支。若独立采用方案 B，则仅把经 A1 到 u_func_dst/D 的匹配路径 false。

未被这条约束 false

方案 A 下可用的 A0 功能路径；方案 B 下不经 A1 的路线、经 A1 到其他终点的路线。

读法 / 验证重点：只写 -from test_mode 不会把 A1→Y 的测试数据路径全部切掉。设置控制位的值，和从控制位出发的路径例外，是两件事。

12

SCAN shift 与 capture 必须分场景

场景前提：扫描触发器 SE=1 选择 SI 移位，SE=0 选择 D 功能输入；测试协议需要分别签核 shift 与 capture。

Tcl · PrimeTime
# 场景 1：SCAN_SHIFT，独立会话/场景
set_case_analysis 1 [get_ports scan_enable]
# 继续配置真实 scan clock、scan_in/out delay，并检查 shift setup/hold

# 场景 2：SCAN_CAPTURE，另一个独立会话/场景
# set_case_analysis 0 [get_ports scan_enable]
# 按测试协议建立 capture / at-speed 时钟与有效数据检查

# 只在 FUNC 场景，且 scan_in 确实完全不使用时的独立示例：
# set_false_path -from [get_ports scan_in]

被 false 的路径

两段模式建模本身都不新增 false-path exception。最后一行若在满足前提的 FUNC 场景启用，则切所有从 scan_in 发出的匹配路径。

未被这条约束 false

SHIFT 场景中的 scan chain 不应被 false；CAPTURE 场景中的有效功能路径也不应被 false。FUNC 中的那条 port 例外不会切内部 scan flop → scan flop 路径。

读法 / 验证重点：scan 时钟很慢仍可能有 hold 问题。不要把 FUNC 的 scan_in 例外加载进 SHIFT 场景；也不能把“test_mode=1”理解成“所有功能数据路径永远不用”。

CHAPTER 05

CDC、mode 与 test：约束背后的电路前提

同步器里，边界路径和同域路径分开看

A 域源寄存器CLK_A
⇢
B 域第一级异步输入边界
→
B 域第二级保留 B → B 检查

异步时钟没有可依赖的固定边沿关系；把这类边界设为 false，并不会解决亚稳态、窄脉冲丢失、多位数据一致性或多个同步信号重汇合的问题。两级同步器适合某些单比特电平场景；总线、脉冲、握手、FIFO 必须采用各自正确的 CDC 结构与协议。

来源与版本边界见第 11 章；PT 与 FC 的报告方法分别见第 7、10 章。

  • 不要仅凭名字或频率判异步。100 MHz 与 200 MHz 可能同源且相关；两个 100 MHz 独立振荡器也可能异步。先查 clock source、generated clock 与架构定义。
  • 保留 CDC 所需的物理预算。例如多位编码跨域可能对位间偏斜、传播延迟有要求。若仍需 max delay / skew 检查，不要先把整个域关系一刀切，再期待补一条命令自动恢复。
  • 全域 clock groups 适合完整的组间关系。若只获批豁免一个同步器入口，示例 2 或更精确的 clock→pin 约束更容易审计；同时也要检查遗漏的 crossing。
  • SI 语义要保留。set_clock_groups -asynchronous 不只是两条 false path 的写法简化，它还表达异步时钟关系并影响串扰分析的到达窗口；不能当作完全可互换的建模。

三种命令怎样选择？

命令表达的设计事实检查与范围
set_false_path某组指定路径的时序检查不适用。可按方向、from/through/to、setup/hold 精确限定；默认两类都豁免。不会自动声明整个时钟域异步。
set_clock_groups -asynchronous组与组之间没有固定相位关系。常规写法排除组间双向时序检查，组内不受该分组关系影响；还传达 SI 的异步窗口语义。
set_multicycle_path数据仍须正确到达，只是允许多拍后捕获。保留有界的 required time；需推导 setup 与 hold 边沿，通常仍可在正常 timing 报告中看到。

FC 手册说明异步时钟在串扰分析中可能使用无限到达窗口；两条方向相反的 false path 不会自动建立这项异步关系。若仍需对部分 CDC 路径检查延迟，FC 本文版本支持 set_clock_groups -asynchronous -allow_paths：保留异步 SI 关系，并允许路径继续分析，再配合经过审核的局部约束。它不是在已有全切关系上随手追加的开关，重叠/重定义可能报错；应从一致的基线建立方案并检查本版帮助。

多周期示例：有意等待 3 拍，不等于 false path

仅假设同一周期、同一相位的时钟，源与目的使能协议保证每 3 拍更新/捕获，目的不会在中间边沿采样。如下常见配对将 setup 放到第 3 拍，并把 hold 拉回原来的同边沿关系。

Tcl · PT / FC · 同频同相的特定前提
# 独立示例；不要与同一路径的 false path 叠加
set_multicycle_path 3 -setup -from [get_pins u_src/CK] -to [get_pins u_dst/D]
set_multicycle_path 2 -hold  -from [get_pins u_src/CK] -to [get_pins u_dst/D]
report_timing -from [get_pins u_src/CK] -to [get_pins u_dst/D] -delay_type max
report_timing -from [get_pins u_src/CK] -to [get_pins u_dst/D] -delay_type min

“N / N−1”不是所有跨频、多相位或不同使能协议的通用公式。要结合 -start/-end 和实际边沿重新推导，再看 max/min 报告中的发射与捕获时间。真正异步的域不能用 multicycle 凑出一个同步关系。

场景分开，证据跟着场景走

场景通常需建模必须保留的检查
FUNC实际功能时钟；test_mode / scan_enable 的功能值。所有可用功能数据路径。
SCAN_SHIFTSE=1；真实移位时钟、scan I/O 约束。SI 链的 setup/hold，尤其跨时钟/锁存器边界。
SCAN_CAPTURESE=0；按协议配置 launch/capture 脉冲。有效功能或 at-speed 测试路径。

异步复位不是“随便全切”的特殊许可。

set_false_path -from [get_ports rst_n] 可能覆盖你本来需要观察的复位释放检查。先区分异步置位/复位与同步释放，确定 recovery/removal 的签核策略；有复位同步器，也要验证其输出到下游的释放行为。

CHAPTER 06

Exception 优先级：按路径、按检查判断覆盖

同一条路径可能同时匹配多个例外。dominant 是最终影响该路径检查的例外；overridden 是匹配了但被覆盖的例外；ignored 还可能由非法起终点或不存在的路径造成，不全是优先级冲突。

入门规则：同等对象范围发生类型冲突时

set_false_path → set_max_delay / set_min_delay → set_multicycle_path。setup 与 hold 分开看，max 与 min 并不是相互覆盖的一对。

还要看对象与路径定义的具体程度。PrimeTime 文档描述了 pin/port 与 clock 的优先关系，同类型例外也有具体范围优先的规则。因而不能把上面的类型顺序扩展成“任何粒度的 false 都永远压过所有其他命令”，也不能相信“写在文件后面的一定赢”。

来源与版本边界见第 11 章；PT 与 FC 的报告方法分别见第 7、10 章。

一个有明确边界的覆盖实验

Tcl · PrimeTime
# 假设 u_src/CK -> u_dst/D 路径存在；数值采用当前时间单位
set_max_delay 5.0 -from [get_pins u_src/CK] -to [get_pins u_dst/D]
set_false_path   -from [get_pins u_src/CK] -to [get_pins u_dst/D]

report_exceptions
report_exceptions -ignored

这里两条命令使用相同的明确 pin 范围，false-path 例外覆盖同一范围的 max-delay 要求。5.0 不再是该路径的有效最大延迟约束；其他未匹配路径不受这两条命令影响。把两行交换顺序，不能当作恢复 max-delay 的方法。

部分覆盖，不等于整条命令失效

假设一条 max-delay 命令覆盖 S→D1 与 S→D2，而另一条 false-path 命令只覆盖同等对象层级的 S→D1：D1 分支被切，D2 分支仍可能使用 max-delay。看报告时必须读范围与 ignored 原因；不能看见一个 overridden 就删除整个原约束。

set_clock_groups 要单独管理。

它排除了组间时钟关系，并不是 report_exceptions 中的一条普通点到点例外。需要保留某些 crossing 检查时，应重新设计分组/例外范围，再验证实际报告。不要依赖一条局部约束“从已经隔离的时钟组里挖洞”。

PT 验证流程：检查豁免与保留的样本

下面采用示例 1 的路径作为检查对象。建议在独立调试会话中做前后对照，保留同一网表、同一场景和同一组选项。

步骤 1 · 留下一份加例外前的基线

2. 对象是否准确匹配集合数目、真实层级、clock 对象名、CP/CK/D 引脚名。
3. 路径身份是否相同from/to/through、先后顺序、launch/capture clock、rise/fall。

5. 是正常检查还是调试展示报告是否 unconstrained；是否显示 false_path 原因。

CHAPTER 08

错误示例 vs 正确示例

这里的“正确”都以所列设计前提已经成立为条件。

① 想切时钟域，却选了时钟 port

错误示例

Tcl · PrimeTime
set_false_path -from [get_ports dma_ep_clk]

只是在指定端口对象，不等于选中由该时钟发射的全部数据路径。

正确示例

Tcl · PrimeTime
set_false_path -from [get_clocks DMA_CLK] \
    -to [get_clocks SYS_CLK]

若真实意图是已批准的 DMA_CLK → SYS_CLK 豁免，应按实际时钟对象和方向声明。port 名和 clock 名可以不同。

② 想双向隔离，却把同域路径也切了

错误示例

Tcl · PrimeTime
set_false_path -from [get_clocks {A B}] \
    -to [get_clocks {A B}]

形成 A→A、A→B、B→A、B→B 四种组合。

正确示例

Tcl · PrimeTime
set_false_path -from [get_clocks A] -to [get_clocks B]
set_false_path -from [get_clocks B] -to [get_clocks A]

只切两个跨域方向。完整异步组关系也可采用经过审核的 clock groups。

③ 同步器两级一起豁免

错误示例

Tcl · PrimeTime
set_false_path -to [get_pins {u_sync1/D u_sync2/D}]

不仅范围覆盖所有源，还切掉了正常的 sync1→sync2 同域检查。

正确示例

Tcl · PrimeTime
set_false_path -from [get_ports async_in] \
    -to [get_pins u_sync1/D]

仅针对已经确认的异步输入边界；继续检查 sync1→sync2。

④ 用 false path 表达固定测试模式

错误示例

Tcl · PrimeTime
set_false_path -from [get_ports test_mode]

它不把 test_mode 固定为 0，也不自动关闭所有测试数据分支。

正确示例

Tcl · PrimeTime
# FUNC 模式，规格要求该信号始终为 0
set_case_analysis 0 [get_ports test_mode]

传播真实模式值，核查被选择的 MUX 输入。其他模式必须独立建模。

⑤ 想切某支路，却豁免整个终点

错误示例

Tcl · PrimeTime
set_false_path -to [get_pins u_dst/D]

来自所有合法源、所有分支到这个终点的路径都可能被切。

正确示例

Tcl · PrimeTime
set_false_path -from [get_pins u_src/CK] \
    -through [get_pins u_mux/A1] \
    -to [get_pins u_dst/D]

若只证明这组起终点的 A1 支路无效，就明确写出三个条件。

还有三种需要立即纠正的思路

  • “报负 slack，所以切掉。”先核对时钟、I/O、模式与真实采样要求，再修设计或约束。不能用例外隐藏有效违例。
  • “get_* 没报错，所以选对了。”集合可能为空、过多或类型错误；显式打印名称与数量，检查 ignored。
  • “旧网表能用，新网表原样用。”重命名、综合优化、DFT 插入、层级变化和派生时钟新增，都可能改变约束覆盖。每次都重新验证。

report_exceptions -ignored
report_clock -groups

# 用与设置时一致的对象范围缩小例外报告
report_exceptions -from $src -to $dst

report_timing -from $src -to $dst -scenarios [current_scenario] \
    -delay_type max -exception dominant
report_timing -from $src -to $dst -scenarios [current_scenario] \
    -delay_type min -exception dominant
例外报告的筛选不是“所有影响该路径的约束”查询。

FC 的 report_exceptions -from/-to 会按原例外的路径说明对象筛选。原来用 clock 设置的约束，不能只用寄存器 pin 过滤而据此认定它不存在。先看不加过滤的报告，再按原 clock/pin/through 形式查询，并结合路径的主导例外。-dominant 表示至少影响一条路径，不等于覆盖了所有预期路径；-ignored 补查完全被忽略的例外，两者分开执行。

3. 需要时启用未约束路径报告

Tcl · Fusion Compiler T-2022.03-SP4
# 保存当前值，调试后恢复
set saved_unconstrained [get_app_option_value -name time.report_unconstrained_paths]
set_app_options -name time.report_unconstrained_paths -value true

report_timing -from $src -to $dst -scenarios [current_scenario] \
    -delay_type max -path_type full_clock_expanded -exception dominant

set_app_options -name time.report_unconstrained_paths -value $saved_unconstrained

这个设置允许工具搜索未约束路径，-exception dominant 则为已找到的路径补充例外信息。它们都不保证枚举所有 false path，也不会恢复被豁免的检查。若命令中途报错，先执行最后一行恢复原设置，再按本机帮助排查。

  • FC 本文版本会对找不到受约束路径的终点进一步搜索未约束路径；有其他可报告路径时，仍需收紧起终点/through 范围。
  • 调试时先去掉 -slack_lesser_than 与 -groups 等筛选：本版它们会排除未约束路径。未约束路径没有可用于签核的有限 slack。
  • 本版 exception 报告不搭配 -path_type short/end/end_detailed；上例使用 full_clock_expanded。
  • 无路径仍可能来自 case analysis、禁用弧、对象/时钟缺失或实际不连通。查看报告和模型，再用保留相同网表、场景的独立基线对照。

4. 再确认应该保留的路径仍受检查

# u_keep 是真实存在、未获豁免的同步终点；请替换成实际对象
report_timing -from $src -to [get_pins u_keep/D] \
    -scenarios [current_scenario] -delay_type max -exception dominant

逐个目标 mode 检查例外，逐个相关 scenario 对照 max/min；确认 required time、时钟边沿、路径身份与预期一致。CDC 还要保留同步器第一级到第二级的同域检查。

删除或覆盖例外要格外明确。

不要把 set_false_path -reset_path 当成“恢复正常检查”：该形式会先清理匹配的既有例外，再施加新的 false path。FC 本地手册在 reset_path/reset_paths 的文字处有不一致，本教程不提供跨工具通用删除脚本；调试对照优先从干净基线重新加载所需约束。正式 SDC 的修改须同时检查重叠例外、clock groups 与所有适用模式。
