## FC / ICC2 中对应的命令

Regular

Tap Assignment

```
# 分配各局部时钟树的 Tap
synthesize_multisource_clock_taps

# 利用常规 CTS 构建局部树
clock_opt -from build_clock -to route_clock
```

Structural

Subtree Synthesis

```
# 综合/优化预定义的局部时钟树
synthesize_multisource_clock_subtrees

# 后续时钟综合与优化
clock_opt -from build_clock -to route_clock
```




先看最容易理解的 H-Tree-Only Flow
### 第一步：定义 H-Tree 和 Tap Driver

```
Ic2_create_ndr_rule -name NDR_2W2S -layer "M4 M5 M6 M7 M8 M9" -space 2 -width 2
Ic2_create_ndr_rule -name NDR_3W2S -layer "M4 M5 M6 M7 M8 M9" -space 2 -width 3


set_regular_multisource_clock_tree_options \
    -clock dma_ep_clk \
    -net dma_ep_clk_buf \
    -topology htree_only \
    -tap_boxes {4 2} \
    -tap_lib_cells [get_lib_cells  {*/DCCKND6BWP6T16P96CPDULVT  */DCCKND8BWP6T16P96CPDULVT  */DCCKND10BWP6T16P96CPDULVT */DCCKND12BWP6T16P96CPDULVT }] \
    -htree_lib_cells [get_lib_cells {*/DCCKND6BWP6T16P96CPDULVT  */DCCKND8BWP6T16P96CPDULVT  */DCCKND10BWP6T16P96CPDULVT */DCCKND12BWP6T16P96CPDULVT}] \
    -htree_layers "M8 M9 M10 M11" \
    -htree_routing_rule "NDR_3W2S"
    
```




### 第二步：真正生成 Tap 和 H-Tree

```
synthesize_regular_multisource_clock_trees
```

原书明确说明，这个命令包含两个阶段：

```
tap_synthesis
      ↓
htree_synthesis
```

执行完成后，你就有了：

```
            CLK
             |
           H-Tree
        / /  |  \ \
      Tap1 Tap2 ... Tap8
```

但此时还不能把这 8 个 Tap 当成已经完成的 8 棵局部时钟树。

还差两个重要步骤。

### 第三步：Tap Assignment

这是整个 Regular Multisource 中最容易忽略的一步。

例如我们已经插入 8 个 Tap，但是原来的 8000 个 FF 不一定已经被正确分摊到这 8 个 Driver。

P385 甚至专门说明，通过 `create_clock_drivers` 一次创建多个 Tap 时，最初可能仍由其中一个 Driver 承担原 Net 的全部 Load。

因此需要：

```
set_multisource_clock_tap_options \
    -clock CLK \
    -driver_objects $tap_drivers \
    -num_taps 8

synthesize_multisource_clock_taps
```

这里 `$tap_drivers` 代表你实际收集到的 8 个 Tap Driver 对象，不能直接照抄为未定义变量。原书要求 `-num_taps` 与 `-driver_objects` 指定的 Driver 数量一致。

那么 Tap Assignment 究竟做了什么？

Tap Assignment 前后对比

执行 Tap Assignment

示意：多个 Tap 虽已放置，但负载还未完成重新分配，部分连接可能跨区域。

在实际工具中，Tap Assignment 不只是重新画几条线。根据 P376，它可能对已有 Clock Cell 进行 Merge/Split，处理 Sink Group，并复制相关约束与属性。

而且并不保证每个 Tap 正好分到 1000 个 FF。分配还要考虑位置、Clock Gate 和其他约束。

### 第四步：完成 Local Clock Tree

```
clock_opt -from build_clock -to route_clock
```

这时候工具才从各个 Tap Driver 往下构建局部 Buffer Tree，连接到 Clock Gate 和 FF Sink，继续处理 Timing、DRC 和时钟布线。

最终：

```
                   CLK
                    |
                  H-Tree
                /   |   \
             Tap1  Tap2 ... Tap8
              |     |       |
             BUF   BUF     BUF
            /  \   / \     / \
           FF  FF FF FF   FF  FF
```

你可以把前两步理解为修建主干道路，第三步划分服务区域，第四步把道路修到每一栋房子。

这就是 P379–380、P400–402 的 H-Tree-Only Regular Multisource Flow。

## 五、那为什么 User Guide 还讲 Clock Mesh？

因为刚才我们讲的是没有 Mesh 的简化版本。

现在给全局分配结构加上 Mesh。

原来：

```
CLK → H-Tree → Tap Driver → Local Tree → FF
```

现在：

```
CLK
 ↓
H-Tree
 ↓
Mesh Drivers
 ↓
Clock Mesh
 ↓
Tap Drivers
 ↓
Local Clock Trees
 ↓
FF
```

你会发现：最下面的 Tap Assignment 和 Local CTS 并没有消失。

只是给 Tap Driver 提供时钟的方式变了。

简化的 Regular Multisource + Clock Mesh 示意。Mesh Driver 向连通网格供时钟，下方 Tap Driver 再驱动各自 Local Subtree。

这里有一个关键的物理区别：

H-Tree 是分支式互连。

Clock Mesh 是横纵金属互相连接的网络，可以由多个 Mesh Driver 共同驱动。

因此 Mesh 的 RC、波形和时序分析比普通 Buffer Tree 复杂。

## 六、有 Mesh 的 Regular Multisource，在 FC 中怎么执行？

这一次严格按照 User Guide P376–377 的流程来看：

|顺序|FC 命令|具体干什么|
|---|---|---|
|1|CTS Constraints / Settings|设置 Clock、Library、NDR、DRC 等|
|2|`create_clock_drivers`|插入 Tap Driver|
|3|`create_clock_straps`|构建 Clock Mesh 金属网络|
|4|`create_clock_drivers`|插入 Mesh Driver|
|5|`synthesize_multisource_global_clock_trees`|建立 Global Clock Tree|
|6|`route_clock_straps`|连接 Mesh 和 Tap Driver|
|7|`analyze_subcircuit`|对 Mesh 做电路级仿真与 Timing 回标|
|8|`set_multisource_clock_tap_options`|配置 Tap Assignment|
|9|`synthesize_multisource_clock_taps`|将 Sink 分配给 Tap|
|10|`clock_opt -from build_clock -to route_clock`|构建 Local Subtree、优化和布线|

另外，Guide 对多电压设计还要求相关 MV 设置与检查，并在流程中启用 `cts.multisource.cell_em_aware` 进行 Cell EM 修复支持。它们不是可以不考虑的通用细节。

为什么会多出 `analyze_subcircuit`？

因为 Mesh 是多个 Driver 连接在一起的互连网络。Guide P398–399 使用 RC Extraction、SPICE 仿真和 Timing Annotation 来提高时序分析精度。这里不能简单地将 Mesh 当成普通单 Driver Net。

所以 Regular Multisource 有 Mesh 的版本，比 H-Tree-Only 版本多了一套 Mesh 创建、布线和分析过程。

## 七、Structural Multisource 又是什么？

现在你已经理解 Regular 了，我们只需要比较它们的局部时钟树怎么生成。

||Regular|Structural|
|---|---|---|
|全局结构|H-Tree 或 H-Tree + Mesh|Guide 所述流程通常采用 H-Tree + Mesh|
|局部入口|Tap Driver|Mesh 上的接入点或预定义 Driver|
|核心动作|Tap Assignment|Structural Subtree Synthesis|
|树结构|允许常规 CTS 重新组织局部树|保留用户定义的 Clock Tree 层级|
|关键命令|`synthesize_multisource_clock_taps`|`synthesize_multisource_clock_subtrees`|

例如：

Regular 的思路是：

> 我提供 8 个 Tap Driver。每个 Tap 到 FF 的局部树，你用普通 CTS 方法帮助我完成。

Structural 的思路是：

> 我已经定义了一定的局部树层级和驱动结构。你可以 Merge、Split、Sizing、Relocate，但要保留我指定的结构要求。

Guide P380–381 的 Structural 流程是：

```
创建 Mesh
    ↓
插入 Mesh Drivers
    ↓
构建 Global Clock Tree
    ↓
临时标注合理的 Mesh Delay / Transition
    ↓
synthesize_multisource_clock_subtrees
    ↓
route_clock_straps
    ↓
analyze_subcircuit
    ↓
clock_opt
```

注意这里与 Regular 不同的一个重要顺序：

在 Structural Flow 中，构建 Local Subtree 前就需要为 Mesh 标注合理的 Delay/Transition，因为此时 Mesh 的完整负载还没有确定，不能直接依赖尚未完成的电路级分析结果。后续完成连接后，再分析实际 Mesh。

对应的：

```
synthesize_multisource_clock_subtrees
```

会执行 Merge、Split、Sizing、Relocation、Routing 和 Refinement 等步骤。原书 P403–406 有详细说明。
