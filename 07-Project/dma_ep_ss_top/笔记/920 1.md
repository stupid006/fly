# CTS / CCD

资料：Synopsys《Running CTS》，`ICC_II_BLI_201912_SG_07_Running_CTS.pdf`。下文页码用课件的 `7-xx`。默认值、适用阶段按这份 ICC II 课件记录，实际 FC/ICC2 版本以本机 `man` 和运行日志为准。

## 1. Classic CTS 和 CCD

| 对比          | Classic CTS              | CCD（Concurrent Clock and Data）     |
| ----------- | ------------------------ | ---------------------------------- |
| 主要目标        | 建树、控制 skew，再优化 data path | 联合调整 clock 和 data，改善 setup/hold    |
| Clock skew  | 尽量满足 skew/balance 目标     | 可以主动引入 useful skew，让关键路径得到更多时间     |
| Post-CTS 优化 | 基本流程主要改非 clock 逻辑        | 改 data path 的同时，也允许增量修改 clock tree |

**Classic CTS 不是不管 skew，CCD 也不是让所有 clock 尽量同时到。** Classic 的基本示意强调 clock/data 分开优化；但它也能开启 timing-aware local skew，不能说 Classic 完全不看 timing。

```tcl
# 二选一：选择 clock_opt 的优化方式
set_app_options -name clock_opt.flow.enable_ccd -value false ;# Classic
# set_app_options -name clock_opt.flow.enable_ccd -value true ;# CCD
```

课件中 `clock_opt.flow.enable_ccd` 默认 `true`。这个选项控制 `clock_opt`；`place_opt` 的 CCD 有单独的 `place_opt.flow.enable_ccd`，不能用前者判断整个流程有没有用过 CCD。

补充：开启 clock power/area recovery 后，Classic 也可能利用 useful skew 做功耗/面积回收。因此“Classic 从来不动 clock、不用 useful skew”太绝对。（7-5、7-18、7-29～34、7-52）

## 2. build_clock / route_clock / final_opto

![[Pasted image 20260920110031.png]]

```text
clock_opt
├─ build_clock
│  ├─ CTS：Initial Clock Tree Synthesis，先建树
│  └─ CTO：Clock Tree Optimization，再优化树
├─ route_clock：布 clock nets，更新 I/O latency
├─ final_opto：Post-CTS timing / DRC 优化
└─ global_route_opt：可选的全局布线优化阶段
```

| 阶段 | 主要工作 | 分段运行 |
| --- | --- | --- |
| `build_clock` | CTS + CTO，建立 clock tree、inter-clock balancing；CCD 下是 timing-driven | `clock_opt -to build_clock` |
| `route_clock` | 实际布 clock nets，更新 I/O latencies | `clock_opt -from route_clock -to route_clock` |
| `final_opto` | 修 setup/hold、max transition/max capacitance；CCD 下同时优化 clock/data | `clock_opt -from final_opto -to final_opto` |

Classic 的 atomic commands 对应关系：

```tcl
# build_clock
synthesize_clock_trees
balance_clock_groups

# route_clock
route_group -all_clock_nets -reuse_existing_global_route true
compute_clock_latency

# final_opto
clock_opt -from final_opto -to final_opto
```

这里 `synthesize_clock_trees` 对应建树及其内部优化，不能理解成只包含 initial CTS、不包含 CTO。上面的 atomic 拆法用于 Classic；课件明确说 **CCD 没有等价的 atomic commands 组合**，CCD 分段用 `clock_opt -from/-to`。

`global_route_opt` 是可选阶段，课件默认跳过；不要和 `build_clock` 内部的 clock GR 混在一起：

```tcl
# 需要 GRO 时才开启；布线相关设置要在运行它之前完成
set_app_options -name clock_opt.flow.enable_global_route_opt -value true
clock_opt -from global_route_opt
```

开启后，完整 `clock_opt` 会跑四个阶段；只想检查某一阶段时，把 `-to` 写清楚。（7-16、7-29～31、7-38）

## 3. Congestion-Aware Initial CTS：VR 和 GR

```text
build_clock 默认：
CTS → Virtual Routing，VR
CTO → Global Routing，GR
```

| 方法  | 怎么估计线                                    | 限制 / 用处                             |
| --- | ---------------------------------------- | ----------------------------------- |
| VR  | 用两点间最短 Manhattan 距离估计线长                  | 快，但不考虑高拥塞区域和 routing blockage 带来的绕线 |
| GR  | 考虑 congestion、blockage、可用 routing layers | 可以绕行或换层，RC/latency 估计更接近最终布线        |

**`build_clock` 前面的 initial CTS 默认不 congestion-aware，因为它用 VR；后面的 CTO 默认已经用 GR。**

```tcl
set_app_options -name cts.compile.enable_global_route -value true
```

这条让 initial CTS 也使用 GR。复杂 floorplan、绕线明显时，可以减少建树估计和实际布线之间的偏差；GR 仍然不等于 detailed routing 完成。

![[Pasted image 20260920111242.png]]

记命名：`cts.compile.*` 主要管 CTS，`cts.optimize.*` 主要管 CTO。该开关课件默认 `false`。（7-16）

## 4. Global skew / Local skew

先统一本文符号：

```text
Llaunch  = launch FF 的 clock arrival / latency
Lcapture = capture FF 的 clock arrival / latency
S = Lcapture - Llaunch
```

- **Global skew**：在同一可比的 clock/balance 范围、scenario 和边沿条件下，最晚与最早 sink arrival 的差，概念上是 `max(L) - min(L)`。
- **Local skew**：有 timing 关系的一对 launch/capture FF 之间的 clock arrival 差。本文用上面有正负号的 `S`；具体 report 的统计口径要看表头。

课件例子：两棵树 global skew 都是 `200 ps`，timing-aware clustering 后，关键 timing pair 的 local skew 可以从 `200 ps` 降到 `67 ps`。所以全局 skew 相同，实际 timing 不一定相同。

Local skew optimization 会把 timing 相关的节点聚在一起、增加公共 clock path，并重点照顾 setup/hold critical pairs。

```tcl
# Classic 中需要显式打开；课件中 CCD 默认启用这两项
set_app_options -name cts.compile.enable_local_skew -value true
set_app_options -name cts.optimize.enable_local_skew -value true
```

**Local skew optimization ≠ CCD。** 前者是 CTS/CTO 的优化能力，Classic 也能用；CCD 还联合调整数据路径，并按 timing 分配 useful skew。（7-17～18）

### Relaxed skew target 的面积 / hold 取舍

Local skew 模式默认会自动推导较宽松的 skew target，有 slack 的地方不必硬追求零 skew，以减少 clock buffer。课件中自动目标有 clock period 的 `3%～10%` 范围限制，这是该课件的算法说明，不是项目通用的手填目标。

日志可能出现：

```text
Computing global skew target..
Setting target skew for clock: SYS_2x_CLK as 0.240000
```

| 做法 | Clock tree | Data path |
| --- | --- | --- |
| 放宽 skew target | 可能减少 clock buffer / clock area | hold 可能变差，需要额外 hold buffer |
| 收紧 skew target | 可能增加 clock area | 可能减少部分 hold 修复代价 |

如果 CTS 后 hold 恶化明显，可以对比关闭自动目标：

```tcl
set_app_options -name cts.common.enable_auto_skew_target_for_local_skew -value false
```

注意：

- 自动目标启用时，课件说明它会覆盖用户指定的 target skew。
- 关闭自动目标不等于关闭 local skew，也不等于强制零 skew；仍要核对实际采用的 target。
- 比较 clock area + data/hold buffer area、setup/hold WNS/TNS 和拥塞，不能只看 clock buffer 少了多少。（7-17～18）

## 5. CRP / CRPR

**CRP** 是公共 clock path 被 early/late 分别计算后引入的悲观量；**CRPR** 是把这部分不合理的悲观去掉。常说的 CPPR（Common Path Pessimism Removal）也是公共路径去悲观的相关叫法，这里沿用课件的 CRPR。

```text
clock root → 公共路径 → common point
                         ├→ launch FF
                         └→ capture FF
```

在常见 OCV 检查中：setup 用 launch late / capture early；hold 用 launch early / capture late。公共部分也被分别计算，会人为加大不利的时钟差异。

课件的同边沿例子，在 common point：

```text
early = 1.58 ns
late  = 1.66 ns
CRP   = 0.08 ns
```

共享的这段物理路径，不应同时承担互相矛盾的 early/late 延迟。CRPR 只去掉公共部分的这项悲观，分叉后各自 clock path 的 OCV 还在；也不是改了真实 clock tree。

```tcl
set_app_options -name time.remove_clock_reconvergence_pessimism -value true

# 看指定寄存器对的 common point、early/late arrival 和 CRP
# FF1/clk、FF2/clk 换成实际 clock pin
report_crpr -from FF1/clk -to FF2/clk
```

课件的 report 写法：setup 在 capture required path 加 `+CRP`，hold 在 capture required path 减 `CRP`。**两者都是去悲观、改善 slack**，不能因为 hold 报表里是负数就理解成 hold 更差。

课件标注该开关默认 `false`，但没有说明默认值的设计原因；“为了兼容或保守”只能算猜测，不写成结论。实际项目要核对实现与签核分析的 CRPR 设置。（7-14～15）

## 6. Boundary FF：先分清“路径”和“寄存器”

Boundary FF 是根据 primary ports 的逻辑连接识别出来的接口寄存器，不是 floorplan 上靠边摆放的 FF。

```text
输入边界：IN → combinational logic → FF1
输出边界：FF2 → combinational logic → OUT

IN → FF1 → internal logic → FF2
     ↑
既是输入路径的 capture，也能是内部 reg2reg 路径的 launch
```

所以同一个 FF 的 clock 调整，可能帮内部路径、却伤接口路径。

### 6.1 ccd.skip_path_groups：哪些路径不用于指导 CCD skew

```tcl
set_app_options -name ccd.skip_path_groups \
    -value {pathgroup1 {scenarioA pathgroup2}}
```

- `pathgroup1`：所有 scenario 中这个名字的 group。
- `{scenarioA pathgroup2}`：只针对指定 scenario 中的 group。
- 被 skip 的 group 仍有 datapath optimization，仍参与正常 timing 分析；**不是 false path**。
- 不能据此认为这些路径碰到的 FF 全部被冻结：同一 FF 仍可能因未跳过的内部路径被调整。课件 7-21 就给了这个例子。
- 在 `place_opt`、`clock_opt`、`route_opt` 中启用 CCD 时都要留意这项设置。（7-20～21）

### 6.3 ccd.optimize_boundary_timing：boundary FF 自身能不能调

![[Pasted image 20260920135924.png]]

![[Pasted image 20260920140820.png]]

```tcl
# 有明确需求才限制 boundary FF；课件默认 true
set_app_options -name ccd.optimize_boundary_timing -value false
```

设为 `false` 后：

- 只有 internal FF 可作为 CCD latency 调整对象。
- 不再调整 boundary FF 自身的 latency。
- 如果 boundary FF 的上游 clock path 和 internal FF 共享，这段 fanin 仍允许被优化；不是整个上游结构都被冻结。

若还要禁止 boundary FF clock fanin 的优化：

```tcl
set_app_options -name ccd.optimize_boundary_timing_upstream -value false
```

原截图是 `boundary_timing=false`、`boundary_timing_upstream=true`，就是限制 boundary FF 自身、保留共享上游的优化空间。两个都设 `false` 会进一步压缩 CCD 能动的 clock tree 范围，课件不建议无差别排除所有 boundary registers。（7-22）

| 设置 | 限制的是 | Boundary FF 还能为了未 skip 的 reg2reg 路径被 skew 吗？ |
| --- | --- | --- |
| `ccd.skip_path_groups` 包含 I/O groups | 某些路径组对 CCD skew 决策的参与 | 可以，前提是该 FF 没有另被限制 |
| `ccd.optimize_boundary_timing=false` | 被识别为 boundary 的 FF 自身 latency | 不可以 |

**这两个作用不一样。** 之前“skip 没生效也没关系，后面的 boundary 选项会等价忽略 I/O”的说法不成立。一个按 path group，另一个按 boundary FF，不能互相替代。

### 6.4 scan/reset 不要把大量 FF 都划进 boundary

![[Pasted image 20260920140909.png]]

Reset、scan enable 等 primary ports 可能连接大量 FF。若它们都参与 boundary identification，很多本来想留给 CCD 优化的 FF 也会被归为 boundary。

```tcl
set_app_options -name ccd.ignore_scan_reset_for_boundary_identification -value true

# 或指定需要从 boundary identification 排除的端口
set_app_options -name ccd.ignore_ports_for_boundary_identification \
    -value {my_en en_A}
```

课件中 scan/reset ignore 默认 `false`；识别依赖与 FF scan/reset pins 的连接，不只是看端口名字。**这里忽略的是边界识别，不是删除 reset/scan 的 timing checks。**（7-23）

![[Pasted image 20260920141411.png]]

这段日志仍识别出 `15294` 个 boundary sinks。即使 scan/reset ignore 已开，也可能还有大量由其他 I/O 连接识别出的 boundary FF；需结合识别日志查原因。日志打印了 `ccd.skip_path_groups` 的配置值，也不代表每个组都有效，仍要看前面的 `Invalid path group` warning。

## 7. prepone / postpone：先看 FF 在路径中的角色

- **Prepone**：clock 提前到，latency 减少。
- **Postpone**：clock 延后到，latency 增加。

对普通同频、同边沿 reg2reg 路径，暂不展开 uncertainty/OCV，只看 skew 的作用：

```text
setup slack ≈ T + (Lcapture - Llaunch) - (Tcq_max + Dmax + Tsetup)
hold slack  ≈ Tcq_min + Dmin - (Lcapture - Llaunch) - Thold
```

| 只调整一个 FF | 对这条路径的 setup | 对这条路径的 hold |
| --- | --- | --- |
| Launch prepone | 有利 | 不利 |
| Capture postpone | 有利 | 不利 |
| Launch postpone | 不利 | 有利 |
| Capture prepone | 不利 | 有利 |

同一个 FF 在前一条路径是 capture，在后一条路径又是 launch，所以不能说“prepone 一定好”或“postpone 一定坏”。CCD 要同时权衡相邻路径和多个 scenario。

```tcl
# 课件示例值，使用设计的时间单位，并非推荐项目值
set_app_options -name ccd.max_prepone -value 0.2
set_app_options -name ccd.max_postpone -value 0.4
```

限制的是允许的 latency 提前/推迟量，限制过紧会削弱 timing 优化空间。课件说明这些限制适用于各 corner，且约束最终 CCD skew；不能理解成 `clock_opt` 用完额度后，`route_opt` 又能累加同样一份。（7-19）

## 8. Clock Balance Point Delay：为什么符号反过来

`place_opt` 的 pre-CTS CCD 还没有真实 clock tree，先在 ideal clock 的 sink 上表达所需 latency，再把 useful skew 要求交给 CTS。（7-52～55）

课件例子，时间单位为 ns：

| Sink | 基准 latency | CCD 希望的 latency | Latency offset | Balance point delay offset |
| --- | --- | --- | --- | --- |
| FF1 | 1.00 | 1.00 | 0 | 0 |
| FF2 | 1.00 | 1.05 | +0.05，postpone | -0.05 |
| FF3 | 1.00 | 0.96 | -0.04，prepone | +0.04 |
| FF4 | 1.00 | 1.00 | 0 | 0 |

给 pre-CTS timing analysis / datapath optimization 看：

```tcl
# 课件中的用户基准约束
set_clock_latency 1.0 [get_clocks CLK]

# 下列命令展示 CCD 产生的 pin offset，帮助理解和查报告
set_clock_latency 0.05 -offset [get_pins FF2/clk]
set_clock_latency -0.04 -offset [get_pins FF3/clk]
```

课件说 **CCD 加在 clock pin 上的这些 network latency constraints 会被 CTS 忽略**，因此 CCD 还会生成 balance point delays，让 CTS 实现所需的相对 skew：

```tcl
set_clock_balance_points -rise -delay -0.05 \
    -offset -balance_points [get_pins FF2/clk]
set_clock_balance_points -rise -delay 0.04 \
    -offset -balance_points [get_pins FF3/clk]
```

用一个简化平衡关系理解符号：

```text
Lphysical(i) + B(i) ≈ 同一平衡目标 C

相对共同基准：ΔLphysical(i) ≈ -B(i)

FF2：B = -0.05 → ΔL ≈ +0.05 → clock 晚到 50 ps
FF3：B = +0.04 → ΔL ≈ -0.04 → clock 早到 40 ps
```

`B` 是平衡计算中的补偿量，不是简单“往这条 clock branch 加 B 的物理延迟”。所以 **postpone 对应负 balance delay，prepone 对应正 balance delay**。

“Normalized to zero” 是把共同 latency 基准扣掉后表达相对目标，不是物理 clock latency 变成 0，也不是 CTS 必须做出绝对 `1.00/1.05/0.96 ns`。实际建树后还受共同 insertion delay、routing、corner 等影响。

```tcl
report_clock_balance_points
report_timing -from FF2/clk -to FF3/D
```

课件的 pre-CTS 报告里，FF2/FF3 的 **ideal** network delay 分别是 `1.05/0.96 ns`；balance point report 的 rise offset 则是 `-0.05/+0.04`。CTS 后还要看 propagated clock 的实际 arrival/skew，不能把 ideal report 当成实现结果。

注意：这里是课件的 `-offset` 例子，不要把“符号相反”随意套到所有 latency/source latency 命令上。正常 CCD 流程会生成这些约束，不需要照抄例子再手工叠加；pin 名、边沿和 corner 也要与设计对应。

## 9. 其他 CCD 选项

### ccd.hold_control_effort

原来记的适用场景保留：hold 很关键、hold 修复困难，或者设计对面积敏感，需要避免新增太多 hold buffer。

```tcl
set_app_options -name ccd.hold_control_effort -value medium
```

课件默认 `low`，可提高到 `medium / high / ultra`，让 CCD 更重视减少 hold 恶化。但限制 useful skew 也可能降低 setup 优化收益，不是越高越好。

**该课件限定：只影响 `clock_opt` 的 `final_opto`，以及 `route_opt` 中的 CCD 优化。** 它控制 CCD 的 setup/hold 取舍，不等同于一般的 hold fixing effort。（7-24）

### ccd.enable_top_wns_optimization

```tcl
set_app_options -name ccd.enable_top_wns_optimization -value true
```

课件默认 `false`。开启后，关注范围从每个 path group 的 WNS path 扩展到**每个 path group 最差的约 300 条 critical/sub-critical paths**；不是整个设计总共只看 300 条。课件说明适用于 `place_opt` 和 `clock_opt build_clock` 中的 CCD。（7-25）

### Targeted CCD

![[Pasted image 20260920144321.png]]

```tcl
# 示例：指定确实需要重点优化的 path groups
set_app_options -name ccd.targeted_ccd_path_groups \
    -value {pathgroup_icgs pathgroup_ram1_in}

# 或通过文件列出重点 endpoints，每行一个实际 pin 名
set_app_options -name ccd.targeted_ccd_end_points_file -value ccd_ep.txt
```

`ccd_ep.txt` 示例：

```text
reg_1/D
reg_2/D
icg1/E
macro_1/En
```

同时指定 groups 和 endpoints 时，targeted CCD 取两者的**交集**。只放确实 critical 的对象，不要把所有路径都列进去。它与 top-WNS 扩展是独立功能，可以单用或组合。（7-25～26）

## 10. 跑完后重点看什么

```tcl
report_clock_qor
report_clock_qor -type local_skew
report_clock_qor -type latency
report_clock_qor -type area
report_clock_qor -type drc_violators
report_clock_balance_points
```

配合关键 reg2reg / I/O 路径的 setup、hold timing report 看结果。（Clock QoR 报告见 7-41）

- **阶段**：用 `Starting/Ending clock_opt / ...` 确认当前阶段，别靠某条内部 GR 日志猜。
- **Skew**：global skew 和 critical pair local skew 一起看；CCD 的 global skew 增大不自动等于 timing 变差。
- **面积 / hold**：clock buffer 少了，还要看 hold buffer 是否增多、总面积是否受益。
- **边界限制**：skip group 是否有效、boundary sinks 数量是否合理、共享上游是否仍可优化，分开查。
- **CRPR**：确认去悲观设置及 common point，避免用虚假的 timing 压力指导 CCD。
- **Balance points**：先核对目标 offset 和符号，再检查 CTS 后实际 skew 是否接近目标。

记住三组区别：**CTS/CTO 是 `build_clock` 内部工作；local skew 不等于 CCD；skip path group 不等于冻结 boundary FF。**
