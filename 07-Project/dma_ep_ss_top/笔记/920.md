Congestion-Aware Initial CTS

build_clock
├─ CTS  = Initial Clock Tree Synthesis
└─ CTO  = Clock Tree Optimization
默认下
CTS 阶段  → Virtual Routing，VR
CTO 阶段  → Global Routing，GR

> **`build_clock` 里面前面的 initial CTS 默认不 congestion-aware，因为它使用 VR。**

后面的 CTO 默认已经会用 GR
VR 不考虑高 congestion 区域和 routing blockage

```
cts.compile.enable_global_route true
```

让 initial CTS 这一段也从 VR 改成 GR

默认 build_clock 前半段 CTS 用 VR 快速建树，不看拥塞；后半段 CTO 用 GR 修正。打开 `cts.compile.enable_global_route` 后，CTS 一开始建树时就考虑 congestion/blockage，因此更接近最终 routing。

当选项为 false 时：  
• CCD 只会使用内部触发器  
工具会进行边界识别，以区分边界和内部触发器。如果你的设计中有连接大量触发器的端口，比如扫描使能端口和复位端口，你可能想排除这些端口在边界识别之外；否则，大多数触发器都会被认为是边界触发器，CCD 的范围就会非常有限。  
• 边界触发器的延迟不会被调整  
• 如果时钟路径与内部触发器共享，进入边界触发器的时钟树扇入可以被优化

ccd.hold_control_effort
hold关键和设计对面积很敏感，需要避免增加保持缓冲区的面积时候使用

Set to medium, highor ultrato reduce hold degradation
仅在保持时间极其关键时使用，因为优化设置可能会影响性能 
只影响 final_opto，以及 route_opt 过程中的 CCD 优化

1. Global Route 阶段最重要的任务之一，就是提前判断哪里 routing resource 不够，然后规划绕行。
2. TA，尽量让线长而直、减少 via 数量        在TA完成后，所有的网络都已经布线，但不是很仔细。有很多违规，特别是在布线连接到引脚的地方。详细布线会努力去修正这些违规。
