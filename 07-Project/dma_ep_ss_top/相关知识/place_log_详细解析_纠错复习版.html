CHAPTER 07

复习速查 FAQ

十个复习问题，集中校正最容易记错的结论。

Q1:为什么优化器单独考核 R2R(reg2reg)成本?

在时序约束正确的前提下，R2R 更能直接反映实现质量，因为起点和终点都在片内。但它仍受 clock period、uncertainty、generated clock、multicycle/false path、derate 和 scenario 影响，不能视为“纯实现问题”。本次 R2R-COST 从 21,538 降至约 260，说明大幅改善；最终全设计 R2RTNS 为 491.1，FuncTT reg2reg 仍有 8,446 条违例、TNS -495.8，不能据此称为 clean 或自动判定 place 合格。

Q2:为什么 ICG 合并放在 final_place 而不是 initial?

日志事实本流程在 initial_opto 后执行 Clock Gate Merging，随后进行 timing/congestion-driven placement。解释这一安排便于在逻辑相对稳定后整理门控拓扑，再优化位置。它是 CTS 前的 clock-gating topology 整理，不代表 CTS 时钟树已建立或定稿；也不是所有工具流程的强制顺序。成本相近不构成等价性或约束完整性的证明，仍需检查 CSTR-013。

Q3:为什么 GR 阶段 M1 几乎没走线(线长 0.77μm)?

日志事实原文记录 M1 线长 0.77μm、每格容量 0.83 轨道，并设置 cell 布线层 M2–M11 与 M1 引脚内连接规则。解释应结合这些规则理解 M1 在本流程中的 pin access 角色。DPT、引脚占用等可能影响资源，但各因素对该数值的具体贡献需结合 route report 确认；GR 不能代替 detail route 的连接结果。

Q4:CCD 为什么在本 log 里“动了 0 个 balance point”?

日志事实原文记录三轮 CCD(行 20166/23073/23239)，其中 round 2 明确输出 0 balance points、0 clock latencies(行 23097)。这说明该处 skew 调整计数为 0，不能推断所有轮次均无任何动作。ccd.skip_path_groups 的三个名字未匹配预期组；若 CTS/PostCTS 仍沿用同一无效配置，这些预期组不会由该列表排除，但是否实际优化 IO 路径仍取决于 CCD target/path group 和阶段选项。

Q5:UIC-105(20,973 条)到底意味着什么?

set_clock_latency -offset -0.1 未成功作用于部分目标，实际 timing model 与脚本预期不一致。日志要求目标符合 clock-sink pin 条件，应核对实际对象与版本规则，不能只按是否 ICG 判断。对 setup/hold 的影响方向和大小取决于 launch/capture、关联时钟、early/late 设置及共同路径等，不能固定背成 ±0.1ns，也不能仅凭“测试时钟较慢”判为无害。应筛选合法目标，并对受影响路径比较修正前后的完整时钟路径与 slack。

Q6:为什么最终 WNS -0.7059 在 FuncTT(typical corner)而不是 ss corner?

日志事实FuncTT 的 in2out 组有 68 条违例，WNS -0.7059ns；原文记录该路径涉及 0.77ns 时钟、5 级逻辑，ss 三 corner 的 WNS 约 -0.54ns。推断这可作为优先检查 IO constraints 的线索，不能证明 IO constraint 就是根因。需对照各 scenario 的 input/output delay、时钟周期、不确定性、OCV/derate、RC 与 library timing，以及具体最差路径。

Q7:为什么 place 结束有 14,644 条 hold 违例? 后面怎么处理?

日志事实末态全设计 NHV 14,644、最差 hold slack -0.1421ns；原文给出 func cbest 场景 12,965 条，其中 reg2mem 11,551 条。此前成本栏为 0 不代表此前绝无 hold 风险，单靠汇总数也不能锁定出现原因。CTS/PostCTS 阶段重点处理 hold，结合传播时钟、数据路径优化等措施，并持续跟踪至布线后。当前先检查约束与主要路径群体；不能假设“建树完成就自动清零”，应按项目签核条件评估。

Q8:WNS 显示正值但 NSV 却有几万，矛盾吗?

先检查指标定义。日志优化器表中的正值可能表示违例幅值/成本，不能直接当成带符号的 slack。本笔记保留日志原数值用于趋势比较，最终时序结论优先核对 report_qor.rpt.gz；上传文本给出的 FuncTT WNS 为 -0.7059ns、NSV 为 30,718。不同场景、path group、全设计汇总和成本函数不可直接混算；若有冲突，需回查原始报告。

Q9:为什么 0.55 的初始密度参数最后升到 0.70?

日志事实原文记录 max_density 0.55 → 0.65 → 0.70，以及对 26.6% movable cells 的局部密度调整。这是不同阶段参数与局部操作的记录，不代表全芯片实际利用率相同变化，也不能单凭上限升高断言更可布。后续 GR 峰值 V 344.8% / H 252.1% 提示局部热点；应结合拥塞图、固定单元、宏周边空间及可用布线资源分析。

Q10:这份 log 里哪些数字最该盯?
  1. R2RTNS 趋势：34,223 → 260.3 → 2,659.9 → 491.1；大幅改善，但非零。
  2. NSV 构成：最终全设计 30,821；结合 in2reg、reg2reg、mem2reg 等组判断定位方向，不直接相加或自动归因。
  3. MaxTrnV / MaxCapV：978 / 2,020，仍有 DRV 存量。
  4. 局部峰值利用率：V 344.8% / H 252.1%；复查对应层和区域，不能与平均利用率混淆。
  5. hold 群体：全设计 14,644，以 reg2mem 为主要检查对象，在 CTS/PostCTS 持续对比。
  6. 消息台账：DFT-005 / SQM-1067 / CSTR-013，以及 UIC-105、GRF-014 等建模问题。
